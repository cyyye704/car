三、各问题的根因和处理边界

1. C168 / interrupt 大于 31
   属于 C251 编译器中断号限制，与设备数据库是两件事。
   使用当前已扩展的 C251 完整重编译，isr.c 的 listing 明确报告：
   C251 COMPILATION COMPLETE. 0 WARNING(S), 0 ERROR(S)。
   本次未修改中断定义、未运行中断二进制补丁；所有被 Git 跟踪的 C/H/A51 源码保持不变。

2. Device not found / STC32G144K-32Bit Series / Vendor AI
   初查时 TOOLS.INI 未注册 STC 数据库和 STCMON251。
   检查期间在 16:01:36 观察到外部新增：
     C:\Keil\UV4\stc.cdb
     C:\Keil\C251\BIN\stcmon251.dll
     C:\Keil\C251\INC\STC\STC32G144K246.H
   TOOLS.INI 同时新增 CDB0=UV4\STC.CDB 和 C251 的 STCMON251 TDRV1。
   这些系统文件不是本次代理写入的；没有执行安装或改动系统 Keil 配置。

   使用 Keil 自带 UVCDB2XML 导出数据库，确定本板的实际记录为：
     Device = STC32G144K246-32Bit Series
     Vendor = STC
     family = C251
     RegisterFile = STC32G144K246.H
   对独立临时工程执行 Keil 的 -n 设备查找：旧名字退出 12，新名字退出 0。
   这证明旧工程元数据与当前设备数据库的名称不匹配。

   已仅在 LED uvproj 中更新 5 个 TargetCommonOption 字段：
     Device、Vendor、DeviceId=63697、RegisterFile，以及 Cpu 中的设备 IROM 元数据。
   这些值均来自 Keil 为准确型号自动生成的临时工程，不是换用其他芯片。
   新数据库的 IROM 起点为 0xFC2800；Target251 内逐飞工程实际链接起点仍为 0xFC4800。
   修复前后 SEEKFREE.lnp 的 SHA256 一致，实际内存分配与编译选项没有变化。
   本次重试前，工程 IROM 描述已由外部更新为 0xFC2800 / 0x3D800；予以保留。
   实际 LNP 中 HCONST/ECODE 仍使用官方的 0xFC4800-0xFFFFFF。

   更换电脑或重装 Keil 后，如没有对应设备支持：
   先说明并批准系统改动，再使用官方 STC-ISP 的“Keil仿真设置”中的
   “添加型号和头文件到Keil中 / 添加STC仿真器驱动到Keil中”，选择 C:\Keil。
   逐飞本手册要求 STC-ISP V6.96F 以上；新版本可能名为 AiCube-ISP，以官方版本为准。
   不要手工伪造数据库记录，或选择别的 MCU 来消除提示。

四、今后若再次出现 L250 的授权检查方法

当前构建已经通过，无需为本次验收重复配置授权。以下步骤仅用于以后出现 L250 时。

1. 打开 C:\Keil\UV4\UV4.exe，进入 File -> License Management。
2. 查看 Product / License 信息是否包含有效的 C251 / DK251 产品授权。
   显示 Evaluation，或只有 MDK-ARM 的授权，都不能证明 C251 已激活。
3. 如果已有学校/单位/个人提供的 C251 授权，按其单机或浮动授权方式配置。
   有效的单机授权可依 Keil 官方文档使用 PSN + CID 获取 LIC，再通过 Add LIC 添加。
   配置授权若要求管理员权限，请手动以管理员身份运行 Keil；本次不执行此操作。
   如没有 C251 授权，需向单位管理员或 Keil 正规渠道确认授权方式。
4. 授权配置完毕后重新执行全量构建，以实际不再出现 L250、0 Error(s) 和新 HEX 为准。
   仅能启动 C251.EXE 或只编译一个 .c 文件，不足以证明完整工程能够链接。
5. 原先已打开的 Keil 窗口可能仍缓存旧设备配置。先处理自己的未保存内容，再重新打开
   磁盘上的 seekfree.uvproj；避免将旧窗口配置重新保存覆盖本次设备修正。

五、VS Code 日常构建

1. 使用 VS Code 打开整个 D:\PROJECTS\car 文件夹，而不是只打开某个 .c 文件，
   也不是仅打开下一层仓库目录。任务位于 car\.vscode\tasks.json。
2. 按 Ctrl+Shift+B，运行默认任务：STC32G: Rebuild LED (Keil C251)。
3. 任务在集成终端输出完整编译日志；Problems 面板可以定位 C251 错误和链接错误。
4. 查看最后日志：Terminal -> Run Task -> STC32G: Show last LED build log。
   或直接打开 D:\PROJECTS\car\.build\led\latest.log。
5. 默认总是全量重编译。脚本还可传 -b / -Incremental 做增量编译；如果没有新 HEX，
   增量空构建不会满足本流程的新产物验收，需改用默认全量任务。

相同命令可在 PowerShell 中执行：
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\PROJECTS\car\scripts\build-led.ps1
查看日志：
  powershell.exe -NoProfile -ExecutionPolicy Bypass -File D:\PROJECTS\car\scripts\build-led.ps1 -ShowLog

ExecutionPolicy Bypass 只对该任务启动的 PowerShell 进程生效，不更改系统执行策略。
脚本使用真实 Keil -r/-t/-j0/-o，等待退出，默认超时 120 秒；不会调用仿真或烧录。
仅在退出码为 0/1、日志包含 0 Error(s)、HEX 时间属于本轮构建且通过 Intel HEX
记录长度/校验和/EOF/非空数据检查后，才输出 VERIFIED 并标记 success=true。
已直接读取 tasks.json 的默认任务并执行其 command/args；本轮全量构建成功，返回 0。
尚未模拟 VS Code GUI 中的键盘操作；默认任务定义、实际执行命令、日志和 HEX 均已验证。

只有构建日志出现 VERIFIED、latest-result.json 中 success=true 且 hexVerified=true，
才进入下面的烧录步骤。这些 USB/按键操作需要你手动完成，本次没有烧录硬件。

1. 使用数据线将核心板 Type-C 接到 Windows。首次验证仅连接核心板 USB。
   100PIN 板的这个 Type-C 直接接 MCU USB_DP/DN，按手册使用 USB HID 下载，
   不需要将它误当成 CH340 串口，也不需要另接下载器。
2. 按住 P32，再按住 RST；松开 RST，最后松开 P32，进入 USB ISP 模式。
   等效方式为按住 P32 重新上电，然后松开 P32。
3. 打开官方 STC-ISP/AiCube-ISP，型号选 STC32G144K246；确认设备列表出现
   (HID1) USB-Writer（HID编号可能随本机枚举变化）。
4. 点击“打开程序文件”，选择上面的最新 SEEKFREE.hex。
5. 点击“下载/编程”，等待软件显示“操作成功”。如提示重新上电，重复进入 ISP 的按键顺序。
6. 下载完成后按 RST 或重新上电，运行程序。该 LED 示例在 P5.2 每 200 ms 切换电平，
   应看到核心板蓝色 LED 闪烁；完整亮灭周期约 400 ms。
7. 没有 HID 设备时先检查数据线和 P32/RST 顺序。外部 IO 反向供电可能使 RST 失效，
   可断开外接 IO，仅接 Type-C 再试。驱动安装或系统变更请先确认需求并批准。

本例 main.c 使用 clock_init(SYSTEM_CLOCK_96M)，时钟由库代码设置；不要仅凭 ISP
界面中的频率选项推断程序实际系统时钟。自动 CDC 下载依赖板内已有合适程序，
首次烧录采用上面的 P32/RST 手动 USB ISP 流程。
